## Context

`Search.query` 当前执行 `time.Parse(time.RFC3339, value)`，因此没有忽略调用者的偏移；问题在于随后固定执行 `UTC().Format("2006-01-02 15:04")`。Jira 将无时区日期字面量按执行查询的账号时区解释，账号使用 Asia/Shanghai 时就会产生八小时窗口偏移。

`Server.creation` 在每次创建和 capabilities 请求中读取 `/myself`，仅使用身份信息。`Client` 持有单一 Jira 上游地址及认证信息，适合承载跨项目共享的账号缓存。目前搜索游标签名覆盖操作、项目、原始查询、分页位置、配置摘要及十五分钟期限，但未绑定账号上下文。运行镜像只安装 ca-certificates，没有通用 IANA 时区数据库。

创建字段通过 `map[string]any` 校验后序列化，其中受支持的日期字符串没有时间转换。标准 `created` 不可由调用者提交；评论时间与 issue.updated 也是原字符串投影。因此本变更修复的是搜索语义，不宣称修复尚未取得现场样本的“创建时间少八小时”。

外部行为依据：

- [Jira /myself](https://developer.atlassian.com/server/jira/platform/rest/v11002/api-group-myself/) 返回当前认证账号及 timeZone。
- [JQL Updated](https://confluence.atlassian.com/jirasoftwareserver/advanced-searching-fields-reference-939938743.html#Advancedsearching-fieldsreference-Updated) 的日期字面量没有时区后缀，按账号有效时区解释。
- [REST 字段输入格式](https://developer.atlassian.com/server/jira/platform/about-the-jira-server-rest-apis/#field-input-formats) 区分纯日期和包含时区的日期时间字段。

## Goals / Non-Goals

**Goals:**

- 保持调用者输入代表的绝对时刻，在非 UTC Jira 账号下正确生成可表达的搜索边界。
- 将 `/myself` 的重复读取压缩为有界、按需、跨项目共享的刷新，同时复用已有创建和 capabilities 调用。
- 对不可用时区、缓存失效、并发取消、账号设置变化和 DST 回拨定义可测试的行为。
- 保留现有鉴权、项目/父资源过滤、请求预算、写入不确定性和严格 JSON 边界。

**Non-Goals:**

- 不为 `/field` 或 createmeta 增加缓存，不缓存 issue/评论/附件可见性或写后核验结果，不单独缓存 createEnabled。
- 不接收无时区搜索参数，不推断调用者所在地，不更改日期字段格式支持范围。
- 不修改 Jira 账号设置、现有工单、Zammad 评论文字或 UI 时区。
- 不改变分钟精度、闭区间操作符、三十天范围上限和非快照分页语义；不实现秒级精确过滤。
- 不重写配置内 filterJql 的日期条件，不引入后台轮询、分布式缓存或新外部依赖。

## Decisions

### 1. 按 Jira client 维护不可变账号快照

在 `internal/jira` 新增账号上下文组件，由 Client 持有。缓存天然绑定上游 origin/context path 和该 client 的认证配置，项目和入站 token 共享；新建 client、重启和配置变更不继承旧快照。

快照只保留原有 reporter 选择所需的 `accountId/name/key`、最小展示身份 `displayName/emailAddress`、时区标识、已加载的 `*time.Location`、时区可用状态、到期时间和上下文 generation。不保存任意 /myself 原始 JSON、组、角色或 avatar/self URL；不得向业务响应扩散新字段。返回不可变结构或拷贝，避免创建组装 reporter 时修改缓存。

账号身份有效与时区可用分别判断：有合法身份但 timeZone 缺失/空白/无法加载时，保留当前身份快照，标记时区不可用；创建及 capabilities 可以继续。带时间查询返回 `503 timezone_unavailable`，不得猜 UTC、容器时区或沿用旧 timeZone。时区必须是显式可加载的 IANA 标识或 UTC；拒绝 Go 的环境相关 `Local` 特殊值，不根据 serverInfo 当前偏移推导命名时区。

备选方案：每个项目单独缓存会重复请求；缓存完整 /myself 会扩大保存的数据范围；将缺失 timeZone 视为整体身份失败会错误禁用创建，均不采用。

### 2. TTL 与刷新状态分离

增加 `jira.accountCacheTtlSeconds`，省略为 300，显式整数范围 0–3600；0 表示禁用已完成快照复用，但仍允许合并正在进行的请求。null、字符串、小数、负值和越界值在启动时返回包含字段路径的脱敏配置错误；必须区分省略和显式 0。沿用配置文件加载、重启生效方式，不新增环境变量或管理端点。

首次需要身份或搜索时区时读取 /myself；TTL 从成功获取身份快照完成时起算。消费者所需部分有效且未过期时不访问上游，空闲时不刷新。创建、capabilities 和时间搜索调用同一个获取方法，而不是各自维护 /myself 请求。

账号快照过期且刷新失败时不使用旧身份或旧时区，不重置有效期。上游读取失败进入固定五秒退避，期满由下一次请求重试；账号获取失败时创建及 capabilities 沿用现有 metadata_unavailable/operation_not_available 行为，时间搜索返回 `503 upstream_unavailable`。身份有效但 timeZone 不可用时，时间消费者使用独立五秒重试节流，避免将缺失时区缓存整整一个 TTL；身份消费者仍可使用未过期的身份。

若身份仍新鲜而缺失时区的独立重试遭遇上游读取失败，时间消费者当次及五秒退避期返回 `503 upstream_unavailable`；身份消费者仍使用尚未到期的身份。失败不延长身份 TTL、不修改 generation；只有成功获取的新身份快照才更新上下文。一次成功响应仍缺失/不支持 timeZone 时，则返回 `503 timezone_unavailable` 并进行时区重试退避。

缓存是否到期与 generation 是否变化无关。TTL=0 时仍保留最近上下文指纹和 generation 供游标比较，不将该记录作为可服务的旧快照。进程重启即可主动清空缓存；账号改时区后的人工运维步骤为重启/重建网关，无需新增清缓存 API。

时区失败的五秒退避也独立于成功快照的 TTL：TTL=0 或身份提前过期时，时间消费者仍等待退避边界，不额外读取 /myself。此时错误结果只携带已观察到的 generation，不携带过期身份；搜索依据 timezone_unavailable 错误类型使用该版本信息，而非通过 Bot 是否存在判断。只需身份的消费者不受时区专用退避限制，仍按自身 TTL 读取；上游运输失败的全局退避继续优先于时区缺失错误。

备选方案：过期后继续使用旧时区可提高可用性，但会静默错查，因此不采用；默认逐请求刷新增加上游往返，改用五分钟 TTL，并提供 0 作为更及时检测的选项。

### 3. 合并刷新并保持请求生命周期有界

同一 client 最多一个 /myself 刷新在途，用互斥锁和完成通知协调，锁内只读写状态，网络调用不持锁。并发消费者共享同一批次结果，不能在 TTL=0 时逐个再次请求。等待者可以根据自身 context 立即退出，不影响仍存活的消费者。

刷新使用发起者所在 Jira 队列槽和已有有界操作 context，同一操作内部仍串行执行。发起者取消时结束它拥有的 HTTP 请求、通知等待者；其他仍有效的消费者可在自己的队列槽中重新选出一个刷新者。发起者或等待者取消不缓存为上游故障，也不触发五秒故障退避。不得使用无界 detached goroutine 或通过取消请求释放槽后继续长时间占用上游；所有请求继续遵守整体 deadline、响应大小及无重定向策略。

备选方案：完全脱离请求 context 的共享后台任务更易保持刷新，但需要额外资源生命周期管理，当前两槽有界队列下不采用。

### 4. 搜索转换是纯时间变换，格式精度保持原合同

先严格校验原始请求和游标，再按 RFC3339 解析成绝对时刻并验证成对、非空、`to > from`、不超过三十天。无时区、缺失一端等输入在时区读取前返回既有 `400 invalid_parameter`。

带时间范围时获取账号快照，将原来的 `from.UTC()/to.UTC()` 改成 `from.In(snapshot.Location)/to.In(snapshot.Location)`；仍生成 `updated >= "YYYY-MM-DD HH:mm" AND updated <= "YYYY-MM-DD HH:mm"`，再与项目及 filterJql 组合。原始带偏移参数留在游标中；不把已格式化的本地字符串当作下一页输入。

同一绝对时刻的 +08:00、Z、-04:00 输入必须产生相同查询；例如 `2026-09-29T10:00:45+08:00` 在 Asia/Shanghai 账号下生成 `2026-09-29 10:00`，在 UTC 账号下生成 `2026-09-29 02:00`。秒与毫秒沿用截到分钟的现有行为，文档明确这不等同于秒级精确过滤。

没有调用者时间范围的搜索不为此额外读取 /myself；配置 filterJql 内的日期继续由 Jira 自身解释，不能从无时区文字推断另一种原意。

### 5. 完整 IANA 规则与回拨歧义保护

由网关二进制嵌入标准库 `time/tzdata`，保证 Alpine 或裸机在缺少系统时区数据时仍能加载完整命名时区规则。遵循 Go 的数据源选择顺序，系统 zoneinfo 或 ZONEINFO 可能优先，因此不承诺不同环境的规则版本完全一致。使用目标日期的偏移，不能把账号当前偏移缓存成 FixedZone。

无时区 JQL 无法区分回拨重复小时。例如 America/New_York 的 `2026-11-01T01:30:00-04:00` 与 `2026-11-01T01:30:00-05:00` 都格式化为 `2026-11-01 01:30`。转换辅助方法必须根据目标时区的转换规则判断最终输出的本地分钟是否在不同 UTC 偏移下重复出现；任一边界存在这种歧义则返回 `400 ambiguous_time_range`，不执行业务搜索。普通一分钟内不同秒不算回拨歧义。上游账号/项目预检读取可能已发生。

检测枚举边界附近的 IANA 时区转换，计算回拨形成的本地重复区间，与最终输出的整个分钟区间求交。不能只依赖一次 ParseInLocation 往返、仅检查分钟的第零秒，也不能假设回拨总是一小时。测试包括 America/New_York、Australia/Lord_Howe 的半小时回拨以及 Europe/Paris 的历史秒级回拨。跨 DST 但两个最终边界均唯一的区间允许查询。

备选方案：继续要求 UTC 账号最简单，但无法满足自动适配；改用数值 epoch JQL 可能避免本地时间歧义，但会改变精度合同且目标 Jira 版本尚未验收，留作单独方案；静默选择重复小时中的一个不可接受。

### 6. 游标绑定上下文版本

Client 保存 generation。首次成功加载建立基线；后续账号稳定身份或时区状态变化（包括已知→不可用→恢复）才递增，普通成功续期、displayName/email 变化和正常 DST 日期偏移不递增。有效时区 ID 变化即视为上下文变化，允许对别名变化采取保守失效。

所有新搜索游标记录当前 generation；无时间查询不强制刷新，但使用已知的版本。续页先比较当前已知 generation，已经不符的游标直接返回 `410 cursor_expired`；带时间的有效续页再按需取得当前快照并再次比较版本。检测到不同不执行该页业务搜索。已知新快照时区不可用且版本改变时，旧游标优先返回 410，新查询返回 503。尚未发现游标失效而运输故障无法建立新快照时返回 503，不伪造版本变化。无时间搜索在其他请求已经发现变化后同样拒绝旧版本游标，从而保守覆盖配置 filterJql 中可能存在的日期条件；它本身不承担主动检测职责。评论游标仍只按原有绑定规则处理。

生成 JQL、执行查询及签发 nextCursor 使用同一不可变快照/generation；不可在签发游标时重新读“最新版本”，否则并发刷新会把旧语义查询错误标记为新上下文。如果查询进行中版本变化，该页仍遵守已有非快照合同，下一页会检测并拒绝旧版本。原有操作/项目/配置/签名/十五分钟期限校验全部保留。

### 7. 失败隔离及接口兼容

创建仍通过相同字段白名单、schema/枚举、createDefaults、固定 bot reporter 和写后归属核验。缓存身份不是授权缓存，绝不跳过父 issue 过滤、评论 visibility、附件归属或 Jira 自身权限检查。身份更新后重新计算 createEnabled，不能长期缓存其派生值；本次不缓存 schema/createmeta。

受支持的创建日期字符串（包括偏移）及 issue.updated/评论 createdAt/updatedAt 保持原值。不得将纯日期、description/comment 中的文字或系统 created 做统一时区补偿。错误和诊断只输出固定代码及允许的字段路径，不回显认证、原始 /myself 响应或 JQL。

## Risks / Trade-offs

- [TTL 内账号变更仍不可见] → 默认最多剩余 TTL 的检测窗口；提供 TTL=0 和运维重启步骤。即便逐次检查，/myself 与搜索之间仍存在外部配置变更竞态，不宣称原子保证。
- [回拨重复分钟无法表达] → 对歧义边界明确拒绝；推荐对需要覆盖此类窗口的同步账号使用 UTC，或后续单独验收 epoch 方案。
- [拒绝使用过期快照降低故障期可用性] → 五秒退避、按需恢复；不影响不需要账号上下文的普通读取/无时间搜索。缺失 timeZone 不等同于身份不可用。
- [时区规则版本与 Jira 不一致] → 嵌入规则随 Go/网关版本更新，真实验收覆盖目标命名时区及 DST；不能将缓存清空等同于 tzdata 更新。
- [账号名称或权限改变] → 缓存只用于身份数据，所有现有授权和写后核验继续执行；上游拒绝不自动重试写入。
- [部署资料与主规格暂有配置迁移差异] → 当前已完成但未归档的 unify-gateway-file-config 保持原状，本变更新配置遵循当前 JSON 装配，不改写其制品或已归档记录。

## Migration Plan

1. 实施配置、缓存、转换和游标逻辑并通过单元/HTTP mock/竞态测试；更新 smoke 的假 /myself 数据及无系统 tzdata 的验证。
2. 文档示例补充 `jira.accountCacheTtlSeconds: 300`；已有配置省略可直接启动。更新 UTC 接入要求为自动识别，并明确错误、精度、缓存窗口及纯创建的边界。
3. 重启部署清空旧进程缓存及游标。使用测试 Jira 项目核对 UTC、Asia/Shanghai、半小时时区、账号变更和缺失字段；未执行时记录“未验收”，不把 mock 结果写成真实验证。
4. 运维手动变更 Jira 账号时区后重启网关，或接受所配置 TTL 的检测延迟。
5. 回滚旧二进制前移除新配置键（旧版严格拒绝未知键），并恢复旧版要求的 Jira 服务账号 UTC 前提；回滚/重启会使游标失效。需要变更真实账号设置时按部署方运维流程执行。

## Open Questions

- 制品层面没有阻塞实施的设计问题。目标 Jira 版本、/myself.timeZone 在继承默认时区时的实际返回，以及创建时间八小时显示差异尚无现场样本；将这些保留为真实环境验收项，不据此扩大本次范围。
